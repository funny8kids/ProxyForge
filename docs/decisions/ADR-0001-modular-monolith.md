# ADR-0001：采用模块化单体，而非微服务

- 状态：Accepted
- 日期：2026-11-01
- 决策者：架构组
- 相关：[ARCH-001](../architecture/01-system-architecture.md)

## 背景

蓝图定义了 13 个业务模块（resource / source / intelligence / verification / pool / policy / gateway / subscription / provider / ai / analytics / audit / auth）。团队规模为个人或小团队，V1 目标是"端到端跑通一条链路"，不是承载高并发。

微服务会带来：分布式事务、服务发现、链路追踪、多套部署编排、跨服务调试成本。这些成本在 V1 阶段换不来任何收益。

## 决策

采用**模块化单体**：单一代码库、单一数据库、单一部署单元（拆为 api / worker 两个进程，共享同一份代码与领域模型）。

模块边界通过以下手段硬化，保证未来可拆：

1. 每个模块有独立包结构（domain / application / infrastructure / interfaces）。
2. 模块间只通过 `XxxFacade` 接口或领域事件通信，**禁止跨模块访问数据表**。
3. 每个模块拥有自己的表，禁止跨模块 JOIN（统计场景走视图/物化视图）。
4. ArchUnit 测试固化依赖方向，CI 阻断违规。

## 后果

**正面**

- 一个事务能覆盖"验证结果 → 端点状态"这类强一致场景，无需分布式事务。
- 本地 `docker compose up` 即可完整运行，开发反馈循环短。
- 重构成本低：改模块边界只是改包结构。

**负面**

- 单体进程内耦合风险：需要靠 ArchUnit 与代码评审持续防守。
- 无法按模块独立扩缩（V1 不需要；Phase 2 可先拆 worker 进程）。
- 单库成为瓶颈（10k 端点量级完全够用）。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| 微服务（每模块一服务） | 运维与调试成本远超 V1 收益 |
| 纯单体（无模块边界） | 半年后无法维护，且拆分需要重写 |
| 事件驱动 + 消息队列起步 | 引入 Kafka/NATS 增加部署复杂度，V1 用 outbox + DB 租约足够 |
