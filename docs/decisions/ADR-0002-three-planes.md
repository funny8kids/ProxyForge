# ADR-0002：Control Plane / Data Plane / Intelligence Plane 三层分离

- 状态：Accepted
- 日期：2026-11-01
- 相关：[ARCH-001 §3](../architecture/01-system-architecture.md)

## 背景

系统同时要做三件性质完全不同的事：发现与分析（慢、不确定、依赖外部 AI）、资源决策（需要事务与一致性）、流量转发（低延迟、高可用、不能受业务影响）。混在一起会导致任何一方的故障扩散到全部。

## 决策

划分为三个平面，并以**进程边界**强制隔离：

| 平面 | 进程 | 关键约束 |
| --- | --- | --- |
| Intelligence | 后台任务（V1 与 api 同进程，Phase 2 独立） | 只写候选区，不写业务表 |
| Control | `proxyforge-api` + `proxyforge-worker` | 产生配置与决策，不碰流量 |
| Data | `gost` 独立进程 | 只执行已编译配置，不理解业务 |

三条硬规则：

1. 控制面**不**在请求路径上（策略在编译期固化）。
2. 数据面**不**回调控制面（控制面轮询引擎状态）。
3. 情报面**不**直接产生"可用资源"（必须经过验证与授权审查）。

## 后果

**正面**

- 控制面宕机时，网关继续按最后一份配置转发——这是可用性的关键收益。
- 引擎可独立升级/重启，不影响管理功能。
- AI 全挂不影响转发与资产管理（见 ADR-0005）。

**负面**

- 配置生效有延迟（编译触发 → 下发，秒级；健康变化 → 重编译，分钟级）。
- 需要处理"配置漂移"（DB 状态 vs 引擎实际配置），通过 `gateway_configs.status` 与定期对账解决。
- 引擎能力成为约束（例如 GOST 不支持某策略时需降级表达）。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| 全部在 Java 进程内（含转发） | 需重写协议栈；GC 停顿影响转发；故障域耦合 |
| 每请求回调控制面做调度 | 增加 10–50ms 延迟，控制面成为流量单点 |
| 用 Envoy/Nginx 做数据面 | 对 SOCKS5 + 多上游选择支持不如 GOST 直接 |
