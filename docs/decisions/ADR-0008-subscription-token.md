# ADR-0008：订阅 Token 只存哈希，配置版本化

- 状态：Accepted
- 日期：2026-11-01
- 相关：[API-001 §4.6](../api/01-api-design.md)、[SEC-001 §5](../security/01-security-design.md)

## 背景

订阅 URL 会被写进客户端配置、聊天记录、截图、CI 变量，泄露概率远高于普通 API Key。同时订阅内容会随资源池变化而变化，排障时需要知道"客户端拿到的到底是哪一版"。

## 决策

1. **Token 格式**：`pf_sub_` + `base64url(32 字节 CSPRNG)`，熵约 256 bit。
2. **存储**：只存 `sha256(token)`，另存前 8 位 `token_prefix` 用于界面识别。数据库泄露不等于订阅泄露。
3. **一次性展示**：创建响应返回明文，之后任何接口都不再返回。
4. **撤销立即生效**：`revoked_at` 非空即 404，不做缓存宽限。
5. **统一 404**：不存在 / 过期 / 撤销 返回完全相同的响应与耗时（恒定时间比较），防止枚举。
6. **版本化**：每次渲染内容变化生成 `subscription_versions`（保留 20 版），带 `pool_version` 与 `content_hash`；支持回滚与"客户端拿到的是哪版"追溯。
7. **缓存控制**：`Cache-Control: private, max-age=300` + `ETag`，禁止共享缓存。

## 后果

**正面**

- 数据库或备份泄露不会直接导致订阅被滥用。
- 撤销可靠（无缓存窗口）。
- 排障可复现（版本历史）。

**负面**

- Token 丢失无法找回，只能重签（可接受，且是安全特性）。
- 每次渲染都写一条版本记录（写放大可控：客户端通常 1–6 小时刷新一次，用 `ETag` 命中 304 时不写）。
- 无法在服务端"查看"用户订阅内容（只能看哈希）——通过版本历史弥补。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| 明文存 token | 泄露即失守 |
| JWT 作为订阅凭证 | 无法即时撤销；体积大；客户端兼容性差 |
| 签名 URL（HMAC + 过期时间） | 可撤销性差（需维护黑名单），且 URL 更长 |
