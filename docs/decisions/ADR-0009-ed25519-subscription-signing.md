# ADR-0009：订阅内容签名采用 Ed25519，签名对象为规范化 JSON

- 状态：Accepted
- 日期：2026-11-01
- 相关：[SEC-001 §6.3–6.5](../security/01-security-design.md)、[API-001 §4.6](../api/01-api-design.md)、[ADR-0008](./ADR-0008-subscription-token.md)

## 背景

现有订阅方案：32 字节 CSPRNG Token → 只存 SHA-256 → 客户端携带 → 哈希比对。这解决的是**身份认证**（请求者是否持有有效凭证），但解决不了**内容完整性**：

- 配置文件下载到本地后可能被第三方（恶意软件、代理工具、同步盘）修改；
- 用户无法判断"这份 YAML 是不是 ProxyForge 生成的"；
- 出现故障时无法区分"平台生成错了"与"本地被改了"。

## 决策

1. **Token 认证保持不变**（SHA-256 存储、一次性展示、撤销即失效）。签名是**叠加**的第二层，不替代 Token。
2. 使用 **Ed25519** 而非 HMAC-SHA256。理由：订阅分发给任意客户端，共享密钥必然被复制到每台设备，泄露即全网可伪造；Ed25519 只需分发公钥，且支持第三方独立验证。
3. **签名对象是规范化 JSON（RFC 8785 JCS），不是 YAML 字节流**。YAML 序列化不唯一（键序、缩进、引号、锚点、行宽），签字节流在不同库上必然验签失败。YAML 只是该模型的展示形式，客户端验签时 YAML → 解析 → JCS → 验签。
4. **信封自带版本与密钥标识**：`alg`、`signatureVersion`、`keyId`、`revision`、`issuedAt`、`expiresAt`、`canonicalHash`。
5. **签名默认关闭**，开启后通过响应头下发，不破坏不支持验签的客户端（FlClash / Mihomo 忽略未知头）。
6. **防重放不靠签名**：签名无法阻止重放"旧的但仍有效"的配置，因此强制 `revision` 单调 + `expiresAt` + Token 撤销三者并存。
7. 私钥存 `secrets`（`kind=SIGNING_KEY`）或只读文件挂载，**永不入库明文、永不返回 API、永不进日志**；`signing_keys` 只存公钥与状态。

## 后果

**正面**

- 客户端可离线验证内容来源与完整性，且不需要保存任何秘密。
- 密钥轮换不影响已分发的客户端（`keyId` + 公钥分发 + 双签过渡）。
- 与现有 Token 机制正交，可独立开关、独立演进。

**负面**

- 增加一个密钥生命周期管理面（生成/激活/退役/失陷），需要 UI 与审计。
- 客户端要真正受益必须实现验签，短期内只有脚本与自研工具会做；主流客户端仍只做 Token 认证。
- 签名增加约 200 字节响应开销（可忽略）。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| HMAC-SHA256 | 共享密钥必须分发到客户端，泄露即失效；无法第三方验证 |
| 对 YAML 字节流签名 | 序列化不唯一，跨客户端验签不稳定（最容易踩的坑） |
| 完整 JWS（JOSE） | 标准但引入依赖与 base64 膨胀；当前场景用自定义信封更轻。保留为 `signatureVersion=2` 的演进方向 |
| 只靠 HTTPS | 传输层保护不能覆盖"落盘后被改" |
| PGP/GPG 签名 | 生态老旧，密钥管理对普通用户过重 |
